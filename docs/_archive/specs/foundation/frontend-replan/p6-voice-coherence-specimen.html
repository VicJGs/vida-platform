Vida's voice — calm, honest, literary

Six principles, drawn from how every phase has already been written. The voice of a good journal: it speaks plainly, never shouts, never flatters, never lies.
Plain, not cleverSay the thing. "Save," not "Submit your changes."
Calm, never urgentNo alarms, no "Act now." The OS waits for you.
Honest, never overclaimsSays what's true now (local-first) vs later (ZK sync).
Warm, not cuteHuman and literary, but never twee or jokey.
Yours, not ours"Your data," "on your device." The user owns it.

Copy that never overclaims

Honesty is a design constraint here, not a nicety — the process doc marks overclaiming copy as WRONG. Three rules, each a side-by-side.
✕ Overclaims

"Zero-knowledge encrypted sync — your data is 100% secure across all devices!"

Sync is M3. In M1 this is a lie.
✓ Honest & staged

"On your device, encrypted. Sync between devices arrives later."

True today; promises only what ships.
✕ Blames the user

"Invalid input. You entered the date wrong."

Accusatory; no way forward.
✓ Teaches the way out

"Dates look like 2026-10-01. Try that format?"

Shows the fix, no blame.
✕ Dead end

"No results."

Leaves the user lost.
✓ Anti-lost

"Nothing matches "quarterly" yet. Try another word, or add one."

Always a next step.

Language — your call

`locale` is already a preference. The open question is which languages ship in M1, and whether the architecture is built i18n-ready from day one. The UI below is the same, in two tongues.

My recommendation: English-first copy in M1, but the architecture i18n-ready from day one (strings externalized, dates/numbers/currency locale-aware — you already store `number_format`, `time_format`, `locale`). That way pt-BR (and others) is a translation pass, not a rebuild. RTL isn't needed for pt/en but the layout stays logical-property-based so it's possible later. Your call: English-first, pt-BR-first, or ship both in M1?
