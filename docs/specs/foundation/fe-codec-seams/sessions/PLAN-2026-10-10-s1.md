## §2. Business Rules (the invariants S1 must hold)
- **BR-S1-1** — Ship **type + convention only**; NO live React hook/instantiation (IR-1/H4). The `ServiceAccess` shape
  and the conventions are the artifact; first-consumer builds the hook. [FACT: s5-conventions.md:63-70]
- **BR-S1-2** — **RATIFY, don't rewrite.** The shipped collection/dashboard adapters are frozen contracts; S1 verifies
  them against the live `@vida/core` API, it does not re-author them.
- **BR-S1-3** — **View = read-only lens; Capability = interactive.** The SavedView seam carries no entity write; any
  write is a Capability (IR-2). [FACT: quality-bar §4.3; ADR-008:71-77]
- **BR-S1-4** — **degrade, never crash** — the ReadProvider convention preserves BR-11 (missing provider → degraded
  note, no throw). [FACT: views/engine.ts:22-82]
- **BR-S1-5** — `enabled_blocks` (palette) ≠ `block_instances` (placements); offered-set: inline=union across page's
  Spaces + global base, standalone=the Space palette (IR-3). [FACT: ADR-008:128-140; offered-set.ts:26-46]
- **BR-S1-6** — **No speculative access type** (critique R1). S1 does NOT prescribe the consumer's injection mechanism
  (no `ServiceAccess` interface); it documents that a consumer obtains each engine via its exported factory and injects
  it by its own choice (Context/hook/singleton — UI-3/first-consumer's call). Reuse the existing `ProviderRead<T>` type;
  invent no new access type. [FACT: s5-conventions.md:63-70; the No-Guessing "don't home the tier forward" rule]
