# Backend Intent — Part A: health-training

> Module: health-training (special-sources module · **recovered domain** — planned in v1, never built, absent from v2: NO schema, NO `@vida/types`, NO service; every token is `[INTENT]` with NO As-is FACT floor except the CR-005 formula + the composed-foundation FACTs — intake.md:10-13; structure-data.md:4; contract.md:6-8 "Designed — not yet coded"). Health/Training is the **Physical Training pillar** — the *exercise* lever on the body — riding a **five-layer spine**: Catalog → Plan → Template → Instance → Log (HT-1; identity.md:4-10). A performed workout **IS** a Sessions `workout` sub-type + a Training-owned `workout_sessions` extension (HT-2, ADR-004); Training NEVER re-implements the session runtime/scheduler. It is a **derivation-light-but-real** owner (volume/PR/1RM derive from per-set logs, then EMIT to Core Health Metrics — it keeps no parallel KPI store) whose planning face rides the Scheduler (`dueIn()`), whose performance face rides Core Metrics (HEA-* health-core), and whose Role/medical face composes health-core's Physical-Role + Medical-Profile providers. Sources read: `docs/features/health/training/{identity,structure-data,business-rules,contract,conventions}.md` (S1) · `docs/intake/health.md` (S2 — the special source: §A OWNS · §B COMPOSES · §C Integration Contract · HL2-HL15 + closing resolutions + CR-005) · `docs/roadmap/m1.1-delivery-plan.md` §9 (S3 — **no MOD-health bucket**; Health is an M1.3-Depth module earning its own delivery plan at its turn, delivery-table:154) · realignment reruns (S4 — **no training rerun exists**; row 21 ALIGNED; the health-core/health-nutrition reruns govern the shared spine only) · service stub (S7 — `packages/core/src/services/health/` **does not exist**).
>
> Boundary note (ADR-020): items with both a derivation/logic face and a state/render face are SPLIT into a service row + a UI row (P6). Training is genuinely service-real (4 designed services: Catalog / Plan / Template / Workout-runtime — contract.md:9-16) with derivations (volume/cardio-load, PR detection, per-side 1RM emission, plan→day projection rules, completion-pct) but its heavy runtime (rest timer / pause-resume / per-set runtime) and heavy KPI store (1RM/volume/PR) are BOTH borrowed: runtime = Sessions (ADR-004), KPI = Core `health_metric_values`. All view surfaces (catalog browser, plan builder, workout logger UI, set-log UI, PR celebration, calendar/agenda render) are UI (P6). The `@vida/core` training services do **NOT** exist — every service row is DESIGNED interface authored at the health build phase (ADR-016/017).
>
> Cross-cutting: workout runtime + scheduler ride **ADR-004 Sessions** (`workout` sub-type + rest-timer/pause/energy/satisfaction runtime + `dueIn()`); performance KPIs (1RM/volume/PR) EMIT into **Core `health_metric_values`** (source=derived) via the health-core Metric service (HEA-01/02/05) — Training is a metric-value PRODUCER, not the owner; plan→day projection rides `dueIn()`/planned-blocks (Calendar renders); exercise technique + Testing/Recovery protocols live in **Knowledge** (kind=`exercise`/`protocol`); Role-linked workouts compose health-core's **Physical-Role** (HEA-24..27) + medically-aware exercise generation reads health-core's **Medical-Profile provider** (HEA-30, `getConstraints`); AI plan/template generation + library/prescription import ride **ADR-015 AI** + **ADR-014 X-ingestion** (opt-in extension-model, `ai_generated`/`authoring_source` flags); provider seams → Journal (daily contribution: workouts·calories burned), Gamification (streaks·PRs → XP), Notifications (workout reminders·deload), Finance (n/a — nutrition-side); notes/tags ride Notes `pages` + Spaces (`entity_tags` + workout-logger capability Block); units (kg/lb) ride Preferences (weight stored SI). Training NAMES the contracts it rides; it does not author them.
