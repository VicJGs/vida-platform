## §2. Business Rules (S1)
- **BR-RL-S1-1 (REL-01/02/04/05/06)** — `createContact` · `updateContact` · `listContacts(filter?)` · `getContact(id)` · `toggleFavorite(id)` over the `contacts` repo. `listContacts`/`getContact` return only non-deleted (soft-delete filter). `createContact` backfills NN-default columns in the create input (`relationship_type:'acquaintance'`, `interaction_count:0`, `is_favorite:false`) because `Repository.create()` returns the **input row**, not DB defaults ([[repository-create-returns-input-row-not-db-defaults]]).
- **BR-RL-S1-2 (REL-03, RL-2)** — `softDeleteContact(id)` sets `contacts.deleted_at` (soft; row still syncs) **and app-layer cascades** its children: `contact_events`, `interactions`, `contact_reminders`, `reminder_group_contacts`, `network_group_contacts` (no-FK convention, schema:14). Cascade is written **defensively/idempotently** over every child table (all 8 tables exist in the schema now — the cascade is complete at S1, not deferred; critic advisory #1). Children have **no `deleted_at`** → they are **hard-deleted** on contact soft-delete (ledger precedent HB-11/RT-17, schema:127). `reminder_groups`/`network_groups` are NOT cascaded (they are not children of a contact — only the junction rows are).
- **BR-RL-S1-3 (REL-17, validation)** — enum inputs validated via the canonical Zod schemas (`RelationshipTypeSchema`, `FrequencySchema`) before the repo write; a bad enum rejects with a typed validation error (async reject, not sync throw — [[factory-service-no-this]]). `relationship_type`(9)/`frequency`(6) are the S1-relevant CHECK enums. **Required-field set (preflight G2):** `CreateContactSchema` requires ONLY `first_name` (schema `notNull`); every other field is `.optional()`/`.nullable()` (defaults applied in the create input). `closeness_tier` is **OPEN vocab** (no CHECK, Preferences-defined) → `z.string().nullable()`, NOT an enum. `UpdateContactSchema` = all fields optional (partial patch).
- **BR-RL-S1-3b (error contract, preflight G1)** — `updateContact`/`toggleFavorite` reject a **missing OR soft-deleted** contact with `ContactNotFoundError`. Mechanism: a soft-delete-aware read (`getContact(id)` applies `isNull(deleted_at)`) → `null` ⇒ throw `ContactNotFoundError` BEFORE `repo.update` (whose internal read is `eq(id)`-only and would otherwise resurrect-edit a soft-deleted person — a PII-integrity hole). Never let the repo's generic `Error('Row not found')` leak — it is mapped to `ContactNotFoundError`.
- **BR-RL-S1-4 (REL-58, C4)** — `social_links` is a typed-JSON `[E]` field `{linkedin?,twitter?,instagram?,whatsapp?}` that **stays** (never retired to tags). The column is plain `text()`; at M1.0 `[E]=[]` so the repo does NOT serialize. Per [[json-t-columns-need-service-serialize-in-m10]] a `text()` column holding JSON needs **service-side `JSON.stringify` on write + `JSON.parse` on read** in a localized boundary cast (Drizzle binds only primitives → an object write throws without stringify). The create/update input accepts `SocialLinks | null` (service stringifies before `repo.create`); all reads parse back to the object.
- **BR-RL-S1-4b (return-type contract, critique B1)** — because `social_links` is parsed on read, the service returns a **view type**, NOT the raw Drizzle Row: `ContactView = Omit<ContactRow, 'social_links'> & { social_links: SocialLinks | null }` ([[drizzle-row-not-assignable-to-vida-types-interface]] — a parsed object isn't assignable to `ContactRow.social_links: string|null`). `createContact`/`updateContact`/`getContact`/`listContacts`/`toggleFavorite` all return `ContactView` (`getContact`: `ContactView | null`). One localized cast at the boundary (knowledge json-boundary precedent). `createContact` re-attaches the parsed object to the input-row return (Repository.create returns the input row, where `social_links` is the stringified value).
- **BR-RL-S1-5 (REL-55, RL-1, ZK-1)** — all PII fields are `[E]`-marked in the schema; **M1.0 `encryptedFields: []`** (pass-through seam; real field encryption = M3, BR-DB6-3, [[m10-repos-use-empty-encryptedfields-seam]]). `contacts` repo built with `softDelete:true`.
- **BR-RL-S1-6 (REL-54, RL-12)** — every write succeeds locally first; the repo's co-transactional `sync_queue` enqueue (create/update/delete) carries LWW sync. No module code needed beyond using the repo.
- **BR-RL-S1-7 (DB-11 reconcile)** — reconcile `@vida/types/relationship.ts` to the schema floor (mirror-only, no behavior): **drop `Contact.tags`** (schema retired the column, G10→entity_tags; **zero code consumers** verified); **add** `Contact.how_we_met`, `Contact.closeness_tier`; **add** `Interaction.energy_given/energy_received/key_takeaways`; **add** `ContactReminder.is_snoozed/snoozed_until/priority`; **add** `ReminderGroup.anchor_type/anchor_days_before`; **add** `NetworkGroup` + `NetworkGroupContact` interfaces. Import `Priority` from `./common` (PRIORITY is canonical there). Enum tuples `REMINDER_GROUP_ANCHOR` already present; `PRIORITY` already in `common.ts`. The reconcile keeps tuple ≡ interface (DB-9 parity).
