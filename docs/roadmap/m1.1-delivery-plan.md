## 1. Why this plan exists

`docs/roadmap.md` set *what* M1.1 builds and in what order (Notes → Preferences → Journals → Spaces → Sessions →
Check-ins). This plan adds the execution layer: for every module, the **traceability chain** —
`Linear issue → OS entity → code home (ADR-018) → intent source → profile → §XXVI/§XXVII flow → DOC spine → gate`.

## 2. The M1.1 delivery model (grounded, decided 2026-08-18)

**Each `MOD-*` is a FULL VERTICAL SLICE, delivered as two gated increments** (§XXVI "every build step runs this
gate"; the module is *operable end-to-end* when its issue closes — "the whole OS operable by hand", roadmap M1):

| Increment | What | Home | Profile | DOC |
|-----------|------|------|---------|-----|
| **① Backend** | `@vida/core` service (CRUD + business logic + Zod) + repository/React-Query wiring, **over the DB-4-authored schema (M1.0 foundation — NOT authored here)** | `core/src/services/<module>` | add-backend-component | `[B]` current-* + `[F]` unit spec |
| **② UI surface** | per-module route (`lazy(() => import('./app/<module>'))`, Zod params, <80 KB) + screens composing the M1.0-built blocks (UI-1 primitives · UI-2 views · UI-3 editor · UI-4 shell) | `apps/web/src/app/<module>` | add-frontend-component | `[F]` unit spec + Visual Gate + `[C]` refresh + `[L]` |

**Why this grain (docs-fixed):** a module's core is a **`@vida/core` service** (`notes-and-pages/contract.md:5,8`);
UI *blocks* are already built in M1.0 and are **not** re-authored here (`notes-and-pages/identity.md`: "not the home
of component specs"); **per-module routes are explicitly "each module's M1.1+ wave"**
(`docs/specs/foundation/ux-1-information-architecture/baseline.md:37,75` + `.../sessions/IMPLEMENTATION-PLAN-2026-08-01-ux-1-information-architecture.md:169`
— `lazy()`, Zod params, <80 KB) composing those blocks. So a module = service ⊕ its route/screen. `[FACT]`
⚠ **Some UI homes hold AR-4 stubs** (`apps/web/src/app/notes/{index,[id]}.tsx` = `<h2>` placeholders; `app/journals/[date].tsx`;
`app/settings` empty): the UI increment **replaces the stub + registers/keeps the route** (`routes.tsx` already has
`notesRoute` `/notes` + `graphRoute` `/graph`) — not a parallel greenfield dir. `app/spaces`·`app/sessions`·`app/check-ins`
do not exist yet (true creates). `[FACT: ls apps/web/src/app]`

**The UI increment carries the Visual Gate** (real-browser, 8 states — the frontend-visual-gate render table); the
backend increment does not. Each increment runs its own §XXVI double-gate.

**Schema** is authored by **DB-4 (M1.0 foundation)** — `core/src/db/schema/<domain>.ts` — as a prerequisite to
M1.1, **not** by these module issues. A module's ① increment consumes the DB-4-authored tables via the repository;
it does not create them. (DB-4's authoring model + flow are DECIDED — Model B, [`schema-foundation-build-flow.md`](./schema-foundation-build-flow.md).) `[correction 2026-08-18]`

### 2.1 Per-issue profile & flow policy

- **Notes · Preferences · Journals · Check-ins**: full 2-increment slice (backend then UI). Backend =
  add-backend-component; UI = add-frontend-component.
- **Sessions**: the AR-5 `foundation/sessions` spine exists (registry + types, **no `service.ts`** — verified);
  increment ① adds the **scheduling/session service** over it (Pomodoro = the `focus_sessions` sub-type, ADR-004 —
  *not* a standalone module), then ② the session/planner surface. `current-*` **refresh**
  (`docs/features/sessions-and-scheduling/` has them).
  ⚠ **Home split (grounded):** ADR-018 §3.2's services enumeration omits `sessions/`, but `reconstructed-structure.md:90`
  DF-7 states **"all other `MOD-*` follow the default"** (= `core/src/services/<module>`), and MOD-sessions is not a
  listed exception → **`core/src/services/sessions` (NEW) is the scheduling-service surface; `core/src/foundation/sessions`
  (AR-5) stays the base spine/registry/types.** This mirrors the ADR-018 §3.3 substrate↔surface pattern (e.g.
  economy↔gamification). Builders: land the scheduler in `services/sessions`, not `foundation/sessions`.
- **Spaces**: the AR-6 `foundation/spaces` backend is **already built** (registry/service/types) — so MOD-spaces is
  **UI-dominant**: increment ① is a thin service-surface exposure only (mostly done), the weight is ② the
  user-facing spaces/tags surface (`apps/web`). Profile add-frontend-component-led. `current-*` **refresh** (`docs/core/spaces/`). `[FACT: foundation/spaces has service.ts]`

## 4. Sub-waves & critical path

```
W1  MOD-notes            (hub — ← DB-6/DB-9/AR-6; unblocks all five)
W2  MOD-prefs ∥ MOD-spaces ∥ MOD-sessions   (all ← MOD-notes; parallel)
W3  MOD-journals         (← MOD-notes, MOD-prefs)
W4  MOD-checkins         (← MOD-journals)
```
**Critical path:** MOD-notes → MOD-prefs → MOD-journals → MOD-checkins (4 modules × 2 increments = 8 gated build
steps). Spaces + Sessions are off-critical-path parallel branches off Notes.

**Head:** MOD-notes #31 (in-degree-14 hub). Within it: increment ① (backend service+schema) is the first build unit.

## 5. Sequencing rules (inherited + M1.1-specific)

- **Notes & Pages before every other module** (roadmap §Sequencing ②) — it is the connective layer 12+ modules pull.
- **Backend increment before its UI increment** within each module (the UI composes the service's data).
- **Per-module routes register in `apps/web/src/app/<module>`** via `lazy()` + Zod params, <80 KB budget
  (`docs/specs/foundation/ux-1-information-architecture/sessions/IMPLEMENTATION-PLAN-2026-08-01-ux-1-information-architecture.md:169`,
  BR-RT-8) — extending `routes.tsx` (AR-4's single central tree), never chrome.
- **`summary(date)` provider registry** is Journals-owned (MOD-journals ①) — it is the engine UX-6's design model
  named as a seam; MOD-journals activates it, MOD-notes' `/summary` block consumes it.
- **⊕agg not in M1.1** — the all-module aggregators (HARD-1, DB-10/11, MIG-1, DB-5) wait for the full M1.1–M1.3
  module set (M1.4). Every M1.1 `MOD-*` blocks them but none is built here.
