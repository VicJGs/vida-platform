## 1. Why this plan exists

`docs/roadmap.md` set *what* M1.0 builds and *in what order*. This plan adds the missing execution layer: for
every M1.0 issue, the **traceability chain** that keeps the code from diverging from the pattern as it is written.

**The anti-divergence chain (every row carries all links):**

```
Linear issue  →  concrete OS entity  →  code home (ADR-018)  →  intent source (ADR/context)
              →  profile  →  canonical flow (§XXVI/§XXVII)  →  DOC spine  →  gate policy
```

If a row is missing a link, the issue is not ready to build.

## 2. The DOC spine (the "proper documentation way" — grounded, not invented)

Each issue's flow rides the toolkit's real 3-level documentation hierarchy. **M1.0 note:** M1.0 builds the
infrastructure *beneath* the 17 feature modules, so no entity has a `docs/features/<module>/` **aspect-doc set**
(those are the feature-module contexts — all M1.1+). But "no aspect docs" ≠ "no context": the doc-ground splits in two —
- **DB spine + adapter (DB-1/6/7/9/10, AR-2)** already have a **live current-context** at
  `docs/infrastructure/database-layer/{current-spec,current-business-rules}.md` (dated 2026-07-25). Their `[B]` mark
  = **refresh that existing context** (grounded, not fresh); the arch docs (`data-flow.md`, `module-dependency-graph.md`)
  are live intent sources. `[FACT: docs/infrastructure/database-layer/ exists; docs/README.md:108]`
- **DS / UI / editor / most substrates** are genuinely **forward-spec-heavy** — their destination docs are ⬜ or
  0-byte stubs (`docs/ui/*.md` ⬜; `docs/editor/*.md` = 0 bytes; `docs/core/spaces/` = README-only front-door, no
  `current-*` yet), so `/documentation-component` harvests intent from the **ADRs** + `@vida/types` and
  `/document-context` *creates* `current-*` fresh. `[FACT: wc -c docs/editor/*.md = 0; docs/ui/README.md status ⬜]`

| Mark | Command | When | Output |
|------|---------|------|--------|
| **[B]** | `/document-context <ctx>` | §XXVI.1a baseline (before build) | `current-spec.md` + `current-business-rules.md` — **refresh** existing (DB spine → `docs/infrastructure/database-layer/`) or **create** fresh (DS/UI/substrates) |
| **[F]** | `/documentation-component <type>:<name>` | §XXVI.1b forward spec | `docs/specs/<bucket>/<unit>/` + session split (PLAN g1 → IMPL-PLAN g2) |
| **[C]** | `/document-context <ctx>` refresh | §XXIX currency (after build) | promote IMPL-PLAN → `current-*`; ⚠"designed-iface" flips enforced |
| **[L]** | `/layer-docs` | after a new code layer lands | subdirectory `CLAUDE.md` from the bounded survey |

**Per-issue canonical flow (code classes):**
`[B] baseline → [F] forward spec → /critique → /preflight → Approval 1 → IMPL-PLAN → /critique → /preflight →
Approval 2 → implement (entity → real code) → review + quality-gate-engineering (enforces §XXIX) → [C] refresh + [L] → commit docs WITH code.`

**Multi-substrate issues (the increment rule · DF-11).** When an issue authors **more than one independent
substrate** — each with its own owning ADR, its own `foundation/<x>`/service home, and buildable against the
others' **public interface** (rides a shared base/peer through its documented API, not by reading a peer's internal
core tables) — it is delivered as **one gated build-step increment per substrate**, each running the full per-issue
flow above, in dependency order; the Issue closes when the census aligns all N homes. This is §XXVI applied
literally ("every **build step** … runs this gate", `standards/process.md:343-344`) and is what `:150`'s
per-increment substrate streaming already assumes. **Home-count is only the detector, not the rule** — the census
counts Home paths (`tracker_sync.py:941-944`), so DB-9's enums+validators (2 homes, 1 deliverable) is **1** gate. A
sub-part that reads its host's core tables directly and cannot be built against a stable public interface without
the host **folds** into one increment — a *declared* fold, precedented by Views (ADR-007) → AR-6 (`:164`), never
implicit. Integration-class issues that wire already-built contexts (HARD-2) are one gate.
`reconstructed-structure.md` marks each issue `⊞N` in its Outcome cell.

**`current-*` home (open-Q RESOLVED):** co-locate at each context's **level-home**, never a new `docs/modules/`:
core-infra → `docs/core/…` · services → `docs/infrastructure/…` · components → `docs/ui/` + `docs/editor/` ·
feature modules → `docs/features/<module>/`. `[FACT: docs/README.md manifest structure; /document-context I2 shared-home rule]`

### 2.1 Baseline Documentation-Gathering Protocol — BINDING on every head's `[B]` step

> Added 2026-07-28 after a **STRUCTURAL triage** (AR-6): the `[B]` step named the *output* (`current-*`) but not
> the *routed input-gathering*, so heads under-gathered and **derived shapes that were already decided** in
> `docs/` (the grain question, the invented `entity_links` source-shape + `link_type`). The `[B]` gate — and
> therefore the whole double-gate — **does not clear until this protocol has run.** No head skips it.

The OS was fully documented across many sessions specifically so **no gaps are left uncached**. Gathering is
therefore a *routing + retrieval* task, never a derivation task. Run, in order:

1. **ROUTE from the map, don't wander.** Start at `docs/README.md` (the manifest: levels × aspects, fill order,
   status tracker) → the scope's **front-door README** (`docs/core/<area>/README.md`) → follow every link it names.
2. **ADRs are NOT the whole truth — read the SCOPED docs.** The ADRs (`docs/core/decisions/`) gesture at decisions;
   the concrete shapes live elsewhere. For the scope, read: `docs/core/architecture/*` (`cross-module-integration.md`
   = integration + entity/DDL shapes; `security-model.md` = per-field **E/P** classification; `module-dependency-graph.md`;
   `data-flow.md`; `performance-strategy.md` = indexes), `docs/core/business-rules.md` (the invariants the scope
   adds/inherits), and the **`ADR-002 §5.20` owed-tables ledger** — read it **before authoring ANY table** (it holds
   the decided DDL for owed foundation tables). For a feature scope also read the `docs/features/<module>/` 5-aspect
   set + its As-is floor.
3. **GREP every entity/term across ALL of `docs/`** (not only the doc you opened) before treating any shape/decision
   as open. Hit a gap → grep harder; the gap is almost always documented under a different route.
4. **NEVER derive or "recommend" a shape the docs already decide.** No `AskUserQuestion`, no `DECISION-N: RECOMMEND …`
   for a decided thing. If — after a *proper* grep — something is **genuinely uncached**, **PRESENT it explicitly and
   without assumption** so Victor decides; do not fill the gap yourself.
5. **Cite + scope the critic.** Every table/enum/field shape in the forward spec traces to `[FACT: file:line]` from
   the gathered set. The independent `/critique`'s **source list = this full gathered set**, not just the docs the
   author happened to open (an under-scoped critic misses decided-elsewhere shapes — the AR-6 failure mode).

**`[B]` DoD (checkable):** the gathered source set is **enumerated** in the spec/task; every shape in the PLAN
either traces to a `[FACT: doc:line]` or is flagged as a **genuine gap for decision** — zero derived-and-passed-off shapes.

### 5.1.1 Full-graph reconcile (Step 7, 2026-07-28 — the b/c/d tracks + db-3/4/8/10 + ar-4/8 + qa-1)

The -a spine (2026-07-27) validated only the boot edges. This pass validated **every remaining M1.0 edge**
per-edge against the ADR contracts, with an independent adversarial critique. Spec:
`docs/specs/fixes/m1.0-dep-graph-validation/`.

**Governing rule this pass established — build-order blocker vs runtime feed.** A dependency-graph edge is a
**build-order blocker** (B's artifact must EXIST before A is built), NOT a runtime feed or a "design-informs"
relation. §5's Depends-on column had conflated them, especially on the UX track: it listed the *downstream*
