## 1. Summary

Vida is a private, local-first vault — but users need real data from the outside world: health from Apple/Google Health, bank statements, book metadata, legal rule-packs, class calendars. This ADR locks how that data crosses the vault boundary, on one honest premise and one universal mechanism:

- **The honest premise: our server is unconditionally blind; full zero-*leak* is not achievable the moment a third party is involved — and we say so.** *We* never see the user's data (ZK-1, absolute). But a third party the user connects to (Apple Health, their bank, an LLM) does see what the user shares with it — that is a real leak we **disclose plainly, never pretend away**. The trust anchor is *"the user already trusts this source and already has data there"*: re-importing from Apple Health is not a *new* loss. `[FACT: ZK-1; EX-1; the ADR-013 "name the third-party observer" honesty rule]`
- **The universal mechanism: device-mediated, never server-proxied.** Every ingestion is **parsed and encrypted on the user's device**; vault rows sync as opaque blobs. **Our server never fetches on the user's behalf and never sees a plaintext import.** ZK-1 holds no matter which integrations are on.
- **Three integration layers, by who owns the integration** (§3.2): **(1) Native** — a curated, first-party set of connectors to trusted major platforms per domain (Apple/Google Health, …), source-direct. **(2) Public-reference** — public datasets (legal rules, prices, ISBN, food DB) shipped as **bundled/bulk opt-in defaults**, queried from a **local copy** so the source never learns *which item* the user cared about (and, if the *whole set* is fetched, not *which category* either). Honest residual: the bulk pull still discloses *that you're a Vida user pulling this corpus* + IP/timing to whoever serves it, and live-price data that can't be fully bundled keeps a per-item leak (§3.2, §6a). These double as the **canonical integration examples**. **(3) User-managed** — a Preferences self-service layer (webhooks + external-API management, Notion-style) with Vida **cookbooks**, where the user does the integration work at their own risk, inside the full guard.
- **Egress is user-driven within our rails.** Data *leaving* the vault (Health CI-6 medical push) is the strictest case — the **user** decides what is sent and to whom, but only inside guardrails Vida establishes: per-target consent, the **union-of-consents** rule (ADR-010 §3.5), an audit trail, **never auto-transmit**.
- **Opt-in, user-owns-risk, manual fallback always; reconcile-on-import via staging.** Every path is off by default; the manual core is 100% functional without any of them (EX-1). Consent is a **grant** on the existing ADR-010 envelope (not a new sandbox). Imports that merge into existing data (Finance conciliation) stage → auto-match → **commit only on user confirmation**.

## 3. Decision

**3.1 The universal ingestion shape: device-mediated, never server-proxied.**
Every external datum enters through the **user's device**: the device fetches/reads the source, **parses and normalizes on-device**, **encrypts** (L2/L3 per EN), and writes vault rows that sync as opaque blobs. **The server is never a fetch proxy and never receives a plaintext import** — it stays a blind relay (ZK-1, EX-1). There is **no ambient network** in an authored capability (ADR-010 §3.5); any reach is a declared, consented, mediated call. A fetch that *could only* work by having the server read plaintext is **refused, not silently downgraded**. `[FACT: FN-9; ZK-1 hard-refusal (INTERP from PJ-11); ADR-010 §3.5 no-ambient-network]`

**An `external_in` fetch is itself an outbound request — so ingress can carry egress.** A fetch's URL/path/params leave the device; a buggy or malicious capability could encode vault data into them (`GET rulepack/?q=<secret>`), making an "ingress" a disguised exfiltration. Therefore the **compositional-exfiltration rule applies to ANY external reach, in or out**: a capability holding **both** a sensitive read **and** any external grant (`external_in_ok` or `external_out_ok`) is a consented exfiltration channel and takes the **union-of-consents** (ADR-010 §3.5) — the outbound fetch's URL/params are treated as egress, not assumed safe because the *intent* is to pull data in. `[FACT: ADR-010 §3.5 compositional-exfiltration; INTERP: a fetch is an outbound request]`

**3.2 Three integration layers, organized by *who owns the integration*.** The guard is not a flat "external toggle"; it is three layers, each with a different builder and a different, disclosed leak profile. All three run on the §3.1 device-mediated mechanism and the §3.3–§3.4 rails.

**Layer 1 — Native integrations (first-party, curated).** Vida builds and maintains a **closed, curated set** of official connectors to the trusted major platforms per domain — Apple Health, Google Health, and peers (banks/brokers as they expose direct APIs). **Source-direct**: the device connects straight to the platform the user *already* uses, so no middleman is introduced, and the only party that sees the data is one the user already trusts with it. This is the **blessed path** and the target end-state for any high-value source. `[INTENT: RESOLUTION — Victor: native set per area]`

**Layer 2 — Public-reference (bundled/bulk opt-in defaults — hides the item, discloses corpus-use).** Public datasets — legal rule-packs, market prices/FX, ISBN/cover metadata, food-composition DB, exercise/skill libraries — ship **with the OS as opt-in defaults** (the user accepts them or not) and refresh as a **complete set** (bundled, or bulk-pulled from a Vida mirror/CDN), then are **queried from a local copy**. Because the fetch is *the whole dataset, never the user's subset*, **the source never learns which *item*** the user cared about — and if the *whole* corpus is pulled (all jurisdictions, not just Brazil), not *which category* either. This is the **strongest cheap mitigation** — no per-item query, no exotic crypto. **The rule: fetch the whole set, never the user's subset** — the moment a refresh is scoped for bandwidth ("just the Brazil tax pack"), the *category* interest re-leaks. **Honest residual (disclosed, not eliminated):** even a whole-set pull tells whoever serves it (the source, or the Vida mirror) *that this IP/device is a Vida user pulling this corpus, and when* — a "you-use-Vida + corpus-category" leak, not a "which-item" leak. And **live prices** cannot be fully bundled: a per-holding price fetch still reveals the user's holdings to the price source — so live prices stay a **residual leak** pending a whole-index pull, oblivious-HTTP relay, or PIR (⚠ future hardening, §6a). These connectors are the **canonical worked-examples** the user-managed cookbooks point back to. `[INTENT: RESOLUTION — Victor: public refs as bundled OS defaults + gather-without-disclosing]` `[FACT: fiscal-legal.md L32-34 — "only leak is which jurisdiction … (metadata, mitigable)"]`

**Layer 3 — User-managed (self-service, honest-disclosed dent).** A **Preferences integration surface** (webhooks + external-API management, in the spirit of how Notion exposes integrations) where the user **does the integration work themselves**, at their **own risk**, with Vida shipping **cookbooks/recipes** for the common trusted platforms. This is the escape hatch for everything not-yet-native and the **foundation the user builds *their own* integrations on** (self-hosted-platform analogy; single-user per SU-1). It is **maximum freedom *inside* the guard, never around it**: a user-authored connector is a user-authored capability (ADR-010) — it runs sandboxed, its credentials stay with the mediator (§3.4), and a connector that both reads sensitive data and reaches out is a compositional-exfiltration channel taking the union-of-consents (§3.1/§3.3). Any third party the user wires up (including a middleman aggregator, if they choose one) is a **disclosed dent, named at the consent gate** — never laundered as "device-side, therefore private." **Third-party-*shared* connectors (one user's integration published to others) stay behind PC-4's deferred community gate — needs Victor's explicit go (§6d), out of scope here.** `[INTENT: RESOLUTION — Victor: Preferences self-service + cookbooks + user-owns-risk; FACT: PC-4 community-deferred L98-100; ADR-010 sandbox]`

**Layers classify by *who owns the connector*, and classification is *temporal*, not fixed.** A source can live in Layer 3 (user-wired) today and migrate to Layer 1 (native) later (§3.8) — so a bank-with-a-direct-API is Layer 3 until Vida ships a native connector, then Layer 1. The **fetch mechanism** (Bluetooth, file, API, feed) is **orthogonal** to layer — a BLE wearable read is *source-direct* like Native but *user-wired* until curated. Layer = builder/owner, not mechanism.

**The honest-leak matrix (disclosed at each consent gate):**

| Layer | Who sees the data | What leaks, to whom | Our server |
|---|---|---|---|
| **Native** | the trusted source the user already uses (Apple/Google Health, their bank) | only what the user shares, to a party they already trusted with it | **blind** |
| **Public-reference** | the source or Vida-mirror that serves the bulk dataset | **which *item*** = hidden (whole set fetched); **corpus-use + IP/timing** = disclosed to the server/mirror; live per-item prices still leak holdings (§3.2 residual) | **blind to content**; a **Vida mirror sees which datasets a device pulls + when** (a named observer, not "neutral") |
| **User-managed** | whatever endpoint the user wires up (their own API key, a webhook target, possibly an aggregator) | **whatever the user configures to send** — disclosed, user-owns-risk | **blind** |

**LLM connections are a separate layer → ADR-015.** Connecting a user's own model (Claude/ChatGPT via their key), and later first-party native LLM integrations, get a **dedicated management page** and are governed by ADR-015 (§3.7), not folded into Layer 3. `[INTENT: RESOLUTION — Victor: LLM via a separate page = ADR-015 foundation]`

**3.3 Egress is a separate, stricter guard.** Ingestion done right never exposes vault content; **egress** — data *leaving* the vault (Health CI-6: push to a medical system) — by definition does, so it gets its own gate: **per-target explicit consent** (not a blanket "allow external"), the **union-of-consents** rule (ADR-010 §3.5 — a capability granted *both* a sensitive read *and* external-out is a consented exfiltration channel and must present that combination conspicuously), an **audit trail** of what left and when, and **never auto-transmit** — egress is always a user-initiated act. Egress is the **most tightly gated grant** in the system. `[FACT: HC-22; CI-6; ADR-010 §3.5 compositional-exfiltration + egress-strictest + "OS never auto-transmits"; PC-4; INTERP from SU-1]`

**3.4 Consent is a grant on the ADR-010 envelope — this ADR supplies its external-data semantics.** An integration is enabled by a **declare→grant→enforce** grant (ADR-010) whose already-declared fields this ADR gives meaning: **`external_in_ok`** (per-source), **`external_out_ok`** (per-target, egress), plus the **layer** (§3.2) and **data scope** (which entities it may read/write). Grants are **revocable**, **fail closed**, and **re-consented on scope change** — reusing ADR-010's machinery, not a parallel one. Shipped integrations (a first-party CSV parser) are trusted code but bound by the same single-mediated-path; user-authored ones (a Spaces Block reaching external data) run in the ADR-010 sandbox. `[FACT: ADR-010 §3.1-3.5 + §3.2 grant fields; PC-3]`

**Credential custody: the sandbox never holds the token.** For a live connection, the encrypted `connection_config` credential is held by the **OS mediation layer**, never handed to sandbox/capability code. A capability requests *"fetch from source X"*; the **mediator injects the credential and makes the call**, returning only the result. A sandboxed capability that could read a decrypted token could also exfiltrate it (§3.1), so it never sees one — the token stays with the trusted mediator, outside the sandbox's reach. `[INTENT; FACT: ADR-010 §3.5 no-ambient-network + mediated-call]`

**Revocation stops future ingestion; already-ingested rows remain user-owned.** Revoking a grant halts all future fetch/import and fails closed. Data **already committed** to the vault (imported transactions, synced ICS events, ingested metrics) **stays** — it is now indistinguishable from manually-entered user data and is the user's to keep or delete via normal per-entity delete. (Revocation cannot un-see what a third-party aggregator already saw, §3.2 — so a local purge would restore no privacy; the row is kept as normal vault data unless the user deletes it.) `[INTENT: RESOLUTION — revoke = stop-future, keep-ingested]`

**3.5 Reconcile-on-import via staging (never silent overwrite).** An import that merges into existing user data (Finance CSV/OFX ↔ manual transactions) follows: **parse on-device → `import_staging` (parsed rows + match metadata) → auto-match** (by date±tolerance, amount±tolerance) **→ user reviews/merges → commit** to the ledger (idempotent write, ADR-004 §3.2.5). The user is **always the final authority**; a parse error flags per-row and **fails loud** (constitution §5); nothing is committed unconfirmed. Feeds that only *add* (ICS events) skip staging but still **dedup by natural key** (`feed_id, uid`) and mark `is_ignored` rather than deleting. `[FACT: intake/finance.md staging/conciliation L45-46,76; intake/learning-education.md ICS dedup L29-95]`

**3.6 Opt-in, user-owns-risk, manual fallback — unconditionally.** Every integration is **off by default**; the **manual core is 100% functional without any of them** (EX-1). Enabling one surfaces a **labeled, per-integration consent** stating the layer (§3.2) and what leaves the device; the user **owns the risk**; consent is **revocable** and **standing until revoked**. No integration is ever a precondition of a core capability. `[FACT: EX-1; HC-10; SK-12; every module's "manual fallback always"]`

**3.7 The LLM layer is separate → ADR-015 (transport vs. cognition).** Connecting a model — the user's own key (Claude/ChatGPT) now, first-party native LLM later — is **not** folded into Layer 3; it gets its **own dedicated management page** and is governed by **ADR-015** (AI under ZK). The split: this ADR owns the **movement + consent** of external data (fetch, parse, encrypt, stage, egress); ADR-015 owns the **model call**. A photo→text pipeline is *both*: ADR-014 consents+moves the image, ADR-015 governs the recognition. **Interim (ADR-015 not yet written):** a model-involving pipeline is **not ungoverned** — the model call falls back to **EX-1/EX-2 defaults** (opt-in · on-device-preferred · cloud model = a consented, disclosed plaintext dent). Nothing runs unguarded in the gap. `[FACT: books OCR "rides AI ADR"; EX-2 two-ADR split; ADR-015 pending]` `[INTENT: RESOLUTION — Victor: LLM on a separate page]`

**3.8 A native connector must be able to REPLACE a user-managed one for the same source (upgrade path).** A source a user wired up in Layer 3 today should **upgrade to a Layer 1 native connector later** ("once we have a good source of users") **without breaking their data**. This requires two things: a **stable integration identity** (a per-source id the grant + ingested rows key to, independent of which layer implements it) **and — the load-bearing half — a declared per-source *normalization contract*** (the field shape/units/timestamps/dedup-key the ingested rows must conform to). The upgrade is "migration of the connector, not the data" **only if both layers emit rows to the same normalization contract**; if the native connector's data shape differs, it is a genuine data migration and must be documented as one. Layers are implementation tiers of one integration contract — *provided that contract is normalized* — not three incompatible silos. `[INTENT: RESOLUTION — Victor: native "once we have users"; the interchangeability constraint + normalization contract]`

**3.9 Ownership boundaries.**
- **Owns:** the device-mediated ingestion/egress contract · the **three-layer model** (native · public-reference · user-managed) + honest per-layer disclosure · the public-reference "fetch-the-whole-set" rule · the egress guard · the external-data grant *semantics* on the ADR-010 envelope · the staging/reconcile pattern · the stable-integration-identity upgrade path (§3.8).
- **Does NOT own** the sandbox/permission machinery (ADR-010) — it *supplies the external-data grant semantics* to it; **nor the write rail** (ADR-004 §3.2.5); **nor the model call** (ADR-015); **nor delivery** of a feed's "new data" alert (ADR-013).
- **Does NOT own** any module's *data* — Finance owns transactions, Health owns metrics; this ADR governs only how external data *becomes* those rows.
- **Does NOT relax ZK-1** — no integration, however configured, can cause **our server** to see plaintext; a third party the user connects to is a *disclosed* observer, not a server-side leak. `[FACT: ZK-1; EX-1]`

**What this decision does NOT do:** it does not pick specific native connectors or vendors (which health platforms first, which OCR engine), per-source auth mechanics (OAuth vs API key vs Bluetooth), the public-mirror/CDN topology, the anonymizing-fetch research path (PIR/OHTTP — deferred hardening), or the exact `import_staging`/`connection_config`/integration-identity columns — those are **build-phase** (owed to ADR-002 §5.20). It locks the **three-layer model + honest bound + egress rule + consent + upgrade path**, not the runtime.

## 4. Options Considered

### Option A — Device-mediated guard, three ownership layers (native · public-reference · user-managed), honest bound, LLM split out (CHOSEN)
- **Rationale:** keeps ZK-1 unconditional (our server blind) across every documented instance while delivering real integrations; organizes by *who owns the integration* (clearer + more honest than a sensitivity spectrum); anchors trust on *"a source the user already trusts and has data with"* so the aggregator problem largely **dissolves** (source-direct native) rather than being managed; makes the public layer **hide which item (and, whole-set, which category) with the corpus-use residual disclosed**; and reuses the ADR-010 envelope + ADR-004 rail (no new sandbox, no new write path). It is also a **foundation the user builds their own integrations on** (Layer 3; third-party sharing stays behind PC-4).
- **Tradeoffs accepted:** we own a curated native-connector program + cookbooks; a user-wired endpoint is a real, disclosed dent (user-owns-risk); public refs cost bundle/bulk bandwidth; egress needs a distinct stricter guard; the stable-integration-identity upgrade path adds design constraint.

### Option B — Server-side ingestion (the server fetches/parses bank/API data and stores it) (REJECTED)
- **Why rejected:** it **breaks ZK-1** — our server would read plaintext financial/health data. The exact invariant the platform exists to hold; refused outright (EX-1, ZK-1 (INTERP from PJ-11 opt-in/protected)).

### Option C — Purist: forbid every third-party touch; manual entry + on-device-direct only (REJECTED)
- **Why rejected:** it bans safe, high-value cases (native source-direct to Apple Health is a party the user already trusts; bundled public refs leak *nothing* about the user) and abandons users whose source offers no direct path. The three-layer model *permits the safe paths and discloses the dented ones honestly* at equal core-ZK guarantee. Over-restriction here isn't extra privacy — it's lost capability. And it contradicts the mature premise: full zero-*leak* isn't achievable with any third party, so pretending a ban delivers it is dishonest.

### Option D — One flat "external integration" toggle (no layers, no ingress/egress distinction) (REJECTED)
- **Why rejected:** it hides the exact differences that matter — a native source-direct read, a bundled public dataset, a user-wired webhook, and a medical-record *egress* are four different risk profiles. A flat toggle would over-block the safe or under-warn the dangerous, and the compositional-exfiltration risk (sensitive-read + external-reach) would be invisible. Honest consent *requires* the layered disclosure.

## 5. Consequences

**Easier:**
- One coherent model covers every module's ingestion (Finance/Health/Books/Skills/Learning/Projects/Spaces/Fiscal) — a new integration is a new connector in one of three layers, not new architecture.
- ZK-1 survives every integration intact (our server always blind); the manual core never depends on any of them.
- Fiscal & Legal is unblocked — its rule-packs are the **public-reference layer**, and gather-without-disclosing is achievable (bundle/bulk).
- The ICS feed (already in schema) becomes a Layer-1/Layer-3 reference implementation, validating the pattern.
- Honest consent: users see *who sees what* per layer before enabling; the public layer hides *which item* (and, whole-set, *which category*) — with the corpus-use/IP residual disclosed, not hidden.
- Layer 3 is a **foundation the user builds their own integrations on** without core changes (third-party-shared connectors stay behind PC-4's deferred gate).

**Harder:**
- We own a **curated native-connector program** (per-platform, per-domain) + **cookbooks** for the self-service layer — ongoing product work, not one-time.
- The device carries the parse/fetch/reconcile load; a staging + reconcile UX + a Preferences integration-management surface to build.
- Egress needs its own stricter guard + audit trail; the union-of-consents UI must be conspicuous.
- Public refs cost **bundle/bulk bandwidth + a mirror/CDN**; the "fetch-the-whole-set" rule must be enforced (a scoped refresh re-opens the leak).
- The **stable-integration-identity** upgrade path (user-managed → native) is a real design constraint to honor from day one.

**Explicitly accepted tradeoffs:**
- Layered honesty over a flat toggle: more consent surface, in exchange for never mislabeling a dent as private and for a genuinely leak-free public layer.
- A curated native program + bulk public mirror over "just call the API": more of our work, in exchange for the strongest honest privacy per layer.
- Device-side everything over server convenience: more client work, in exchange for unconditional ZK-1.

**Owed schema/build** (build-phase — tracked in ADR-002 **§5.20**, no DDL into its body per D5):
- **ADD:** `import_staging` (parsed rows + match metadata + per-row status; reconcile-on-import).
- **ADD (where a live connection is authored):** encrypted `connection_config` (credentials/tokens at L2/L3; custody by the OS mediator, §3.4).
- **ADD:** an **integration-identity** anchor (stable per-source id decoupled from which layer implements it) **+ a per-source normalization contract** (field shape/units/dedup-key both layers emit to) — §3.8, enables user-managed → native upgrade without data migration.
- **ADD (public-reference trust):** **dataset provenance + signature/version verification** — a bundled/mirrored public dataset (esp. legal rule-packs) must carry a verifiable source + version + integrity signature; a poisoned rule-pack is a correctness-and-legal hole. Build-phase, but named as owed (not silently a runtime detail).
- **DECISION (owed, not runtime):** the **native-set curation policy** — how a platform qualifies for a first-party connector (trust bar · security review · deprecation). Victor decides *which*; the *qualification process* is owed.
- **AMEND (ADR-010 `capability_grants` — semantics, fields already declared):** give meaning to `external_in_ok` (per-source + layer), `external_out_ok` (per-target, egress) + a data-scope; no new column names, no new table (ADR-010 owns them).
- **SERVICE (client):** the three-layer ingestion pipeline (fetch/read→parse→encrypt→stage→commit), the native-connector adapters, the **public-reference bundle/bulk-refresh + local-query** engine, the Preferences self-service integration surface (webhooks + API + cookbooks), the egress guard + audit, dedup-by-natural-key for feeds.
- **SERVER (Vida infra, ZK-blind):** an optional **public-dataset mirror/CDN** (serves whole datasets in bulk; learns nothing about user interest).

## 6. Review Date / trigger

Reconsider if: (a) a public dataset is too large/volatile to bundle or bulk-mirror and must be fetched per-item live (→ adopt oblivious-HTTP/PIR to close the public layer's per-item residual, §3.2); (b) a source offers a **verifiably ZK** connection (client-side tokenization) that would promote a user-managed dent to a native pure-ZK connector; (c) egress demand grows beyond Health CI-6 into a general pattern (→ a dedicated egress ADR); (d) the user-managed layer's platform ambition grows toward third-party-authored connectors shared between users (→ reopen PC-4's community bridge, which needs Victor's explicit go); or (e) the AI boundary (§3.7) proves too entangled to keep ADR-014/015 separate. Otherwise revisit when the first real integration (a native Health connector, Finance CSV import, or the ICS feed hardening) is built.
