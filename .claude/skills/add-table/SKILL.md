# Add a new SQLite table to the local-first schema.

## Inputs

- the feature's structure-data.md row for the table
- which fields are encrypted ([E])
- the enums it uses

If an input is missing, ask; never guess.

## Rules for this operation

- Column conventions: PK = UUIDv7 TEXT generated client-side; timestamps = Unix ms INTEGER; money = INTEGER cents; booleans = INTEGER 0/1; calendar dates = TEXT YYYY-MM-DD; JSON = stringified TEXT.
- Every syncable table spreads `...baseColumns` and `...syncColumns` from schema/_shared.ts; never hand-repeat the `_sync_*` columns.
- Enums are `as const` tuples in @vida/types with the union type derived from the tuple; never a TS `enum` or a bare union. `z.enum(TUPLE)` in @vida/core and the SQL CHECK list are sourced from the tuple (enum-parity.test.ts enforces it).
- Never add an inline `notes` column: notes live in `pages` via entity_type/entity_id.
- Migrations are hand-written SQL in packages/core/src/db/migrations, forward-only (no down()), registered in runner.ts ALL_MIGRATIONS; never edit a merged migration, add the next number.

## Steps

1. Read the governing ADR + the feature's structure-data.md and packages/core/src/db/CLAUDE.md.
2. Add the enum tuples and the entity interface (extends SyncableEntity, `/** @encrypted */` on [E] fields) to the domain file in packages/types/src, export from index.ts, rebuild @vida/types dist.
3. Add the Drizzle table to packages/core/src/db/schema/<domain>.ts with the _shared.ts helpers and CHECKs from the tuples; register its entity_type in _registry.ts if it is linkable.
4. Write the next-numbered migration in packages/core/src/db/migrations and append it to ALL_MIGRATIONS in runner.ts.
5. Add the z.enum validators in packages/core/src/validators and extend enum-parity.test.ts.
6. Write a better-sqlite3 test that migrates from scratch and round-trips a row through the repository.
7. Run `pnpm check`.
